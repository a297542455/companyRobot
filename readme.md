## 一、Java 基础（自动化必备核心）

**1、List、Set、Map 的区别？各自在测试数据存储、参数化、结果校验中的使用场景？**

1\. List：有序可重复，适合存储有序测试用例数据、接口返回列表结果、批量参数化数据；2\. Set：无序不可重复，适合去重场景，如校验页面下拉选项无重复值、过滤重复测试数据；3\. Map：键值对存储，适合存储键值格式测试数据、接口入参封装、测试结果字段映射、Excel/JSON参数化数据读取。

**2、String 常量池是什么？自动化字符串比对常见坑点？**

Java为了节省内存，会将常用字符串缓存到常量池，相同字面量字符串复用地址。常见坑：代码动态拼接、接口返回字符串、页面获取文本不会进入常量池，此时使用==判断会不相等。自动化规范：所有文本、接口字段比对**一律使用equals**，杜绝==比较字符串。

**3、什么是线程安全？自动化脚本并发执行为什么会出现数据污染？如何解决？**

线程安全指多线程并发访问共享资源时，不会出现数据错乱、覆盖、异常的特性。自动化污染原因：多用例并发共用同一个 WebDriver、同一个测试数据集合、全局变量，导致用例互相干扰、登录态混乱、参数覆盖。解决方案：1\. 用 ThreadLocal 隔离驱动和全局变量；2\. 每个用例独立上下文、独立测试数据；3\. 并发场景使用线程安全集合（ConcurrentHashMap、CopyOnWriteArrayList）；4\. 消除全局共享资源。

**4、Collections 工具类常用方法？自动化数据处理有哪些用途？**

**Collections 工具类介绍**

Collections 是 Java 集合工具类，专门用来辅助操作 List、Set、Map，提供大量静态方法，解决集合空指针、排序、数据极值、随机打乱、线程安全转换等问题，是自动化数据处理的常用工具。

**一、常用核心方法（自动化高频使用）**

1、**emptyList\(\) / emptySet\(\) / emptyMap\(\) 空集合**
作用：返回不可变空集合，避免返回 null，杜绝空指针异常。
自动化场景：接口返回空列表、查询无数据时，用空集合接收，防止后续遍历、校验报错。

2、**sort\(\) 集合排序**
作用：对 List 集合进行升序/自定义排序。
自动化场景：校验前端列表、时间、金额、序号是否按规则正序、倒序展示，验证前端排序功能是否正常。

3、**max\(\) / min\(\) 极值获取**
作用：获取集合最大值、最小值。
自动化场景：校验列表最大金额、最小时间、最大序号，验证边界数据展示正确性。

4、**shuffle\(\) 随机打乱**
作用：打乱集合顺序。
自动化场景：测试随机推荐、随机排序、题库随机出题等业务场景。

5、**synchronizedList\(\) 线程安全转换**
作用：把普通非线程安全集合，转为线程安全集合。
自动化场景：TestNG多线程并发执行用例时，共享测试数据集合，防止数据错乱、覆盖。

6、**reverse\(\) 反转集合**
作用：反转列表顺序。
自动化场景：校验倒序排列、最新数据置顶等业务逻辑。

**二、自动化项目整体用途（面试总结版）**

1、**防报错**：用 emptyList 替代 null，避免集合空指针崩溃；
2、**数据校验**：通过排序、极值、反转，校验前端列表展示、排序规则、边界数据正确性；
3、**并发安全**：多线程执行用例时，将普通集合转为同步集合，解决并发数据污染；
4、**场景覆盖**：通过shuffle随机打乱，覆盖随机业务场景，提升测试覆盖率。

**三、10秒面试极简背诵版**

Collections是Java集合工具类，常用空集合获取、排序、极值、打乱、线程同步方法。自动化中主要用来防止集合空指针、校验前端列表排序和边界数据、处理随机场景，同时解决多线程并发测试的数据安全问题。

## 二、Selenium 自动化测试（Web UI 经典技术栈）

**1、隐式等待、显式等待、强制等待的区别、优缺点及适用场景**

1\. 强制等待（Thread\.sleep）：固定休眠时间，稳定性差、执行慢，仅用于特殊弹窗、极少不稳定场景；2\. 隐式等待：全局统一等待时长，针对所有元素，无法针对单个元素定制，存在隐性坑；3\. 显式等待（WebDriverWait）：针对指定元素、指定状态自定义等待条件，灵活、高效、稳定性最强，是自动化首选等待方式。

**2、页面常见等待问题：元素可见、可点击、存在的区别？如何处理元素闪现、抖动？**

1\. 元素存在：DOM中加载完成，不一定可见；2\. 元素可见：页面展示、可视；3\. 元素可点击：可见且无遮挡、可交互。处理闪现、抖动：使用显式等待锁定元素状态，增加重试机制，避免操作过快；优先等待页面加载完成后再执行元素操作。

**3、Selenium 不稳定的常见原因？如何提升脚本稳定性（防抖动、重试、等待策略）？**

不稳定原因：等待策略不合理、页面异步加载、元素抖动、网络波动、浏览器版本适配问题。优化方案：统一显式等待规范、封装元素操作重试机制、操作前校验元素状态、关闭浏览器自动更新、线程隔离驱动、清理缓存，大幅提升脚本通过率。

**4、解释 PageObject 设计模式，为什么 UI 自动化必须用 PO？如何避免用例与元素耦合？**

PO模式将页面元素定位、页面操作方法封装在页面类中，测试用例只调用方法、不直接操作元素。核心优势：解耦元素与用例，页面改版仅需修改页面类，无需改动大量用例，大幅降低维护成本，是UI自动化标准化必备规范。

## 三、Playwright 专项（重点考察，当前主流 E2E 方案）

**1、Playwright 相比 Selenium 的核心优势是什么？速度、稳定性、架构层面分别说明**

1\. 架构：Playwright基于浏览器原生协议CDP，无需中间驱动，架构更简洁；Selenium依赖WebDriver中间层，链路更长；2\. 稳定性：Playwright自带智能自动等待，无需手动写大量等待逻辑，解决元素抖动、加载延迟问题；3\. 速度：启动更快、执行效率更高，支持并发、分片执行；4\. 功能：原生支持录屏、trace追踪、网络拦截、弱网模拟，无需额外封装。

**2、Playwright 支持的浏览器、运行模式（headless/headed）区别与适用场景**

支持Chrome、Firefox、Safari、Edge等主流浏览器。1\. headless无头模式：无浏览器界面、占用资源少、执行速度快，适用于CI/CD流水线、批量回归测试；2\. headed有头模式：展示浏览器界面，适用于本地调试、问题排查、新用例编写场景。

**3、Playwright 自动等待机制是什么？和 Selenium 手动等待对比优势？**

Playwright 所有操作自带智能自动等待，会自动校验元素可见、可交互、网络请求加载完成后再执行操作。对比Selenium：无需手动编写大量显式等待代码，原生规避80%以上的页面加载超时、元素未就绪报错，代码更简洁、稳定性远超Selenium。

**4、如何处理页面异步加载、组件懒加载导致的页面空白/元素延迟？**

1\. 利用Playwright原生自动等待，无需手动休眠；2\. 等待页面关键元素、网络请求加载完成；3\. 针对懒加载组件，先触发页面滚动、聚焦等操作；4\. 开启trace调试，排查加载延迟节点，针对性优化等待逻辑，保证用例稳定执行。

**5、Playwright 如何实现截图、录屏、trace 追踪？回归测试如何利用 trace 定位失败原因？**

1\. 截图：支持页面全屏截图、元素截图；2\. 录屏：全局配置开启视频录制，保存执行全过程；3\. trace追踪：记录每一步操作、DOM状态、网络请求、日志。回归失败后，通过trace可视化文件可精准查看报错节点、页面状态、请求异常，快速定位是脚本问题、页面BUG还是环境问题。

**6、Playwright 如何模拟网络弱网、断网、接口拦截、请求篡改？**

在Playwright自动化框架中，我会通过网络拦截能力实现接口拦截、篡改、Mock，覆盖常规功能测试无法触达的边界异常场景，弥补纯UI自动化的短板。① 网络拦截：通过page\.route\(\)拦截前端所有请求，可拦截指定业务接口、静态资源、无用埋点接口，屏蔽外部不稳定接口干扰，稳定用例执行；② 接口Mock：可直接篡改接口请求参数、请求头，或修改后端响应数据，手动构造**接口超时、返回空数据、返回异常报错、参数非法、权限不足**等各类异常场景；③ 异常场景自动化落地：不再只测正常流程，可自动化覆盖断网、弱网限流、接口500/404、数据为空、数据超限、重复提交等边界异常，校验前端弹窗提示、状态兜底、报错容错逻辑是否正常，大幅提升测试覆盖率，提前发现前端容错性BUG。

**7、Playwright 如何执行批量用例、并发执行、分片执行？**

支持原生并发配置，可设置并发线程数，批量执行全量回归用例；支持分片执行，将用例拆分多批次并行运行，大幅缩短回归耗时；同时搭配用例分组、失败重试，适配大规模自动化回归场景。

**8、从 Selenium 迁移 Playwright 的改造难点和优化点？**

改造难点：原有Selenium元素定位、等待逻辑、工具类需要重构，适配Playwright语法与机制。优化点：删除冗余等待代码、利用Context隔离解决数据污染、借助trace快速排查问题、提升用例执行速度与稳定性，降低长期维护成本。

## 四、E2E 自动化测试思维与流程

**1、你理解的单元测试、接口测试、E2E 测试的分层边界？如何分工覆盖不重复？**

1\. 单元测试：聚焦代码层级，测试方法、逻辑、边界值，由开发主导；2\. 接口测试：聚焦服务接口，校验入参、出参、业务逻辑、异常场景，覆盖后端核心能力；3\. E2E测试：聚焦用户真实操作场景，校验页面交互、流程连通、端到端业务闭环。分层原则：底层问题单元/接口测试拦截，上层E2E只测用户核心流程，避免重复覆盖，提升测试效率。

**2、自动化用例筛选标准：哪些用例适合自动化、哪些不适合？回归用例如何沉淀？**

适合自动化：核心主流程、高频回归、稳定不变的业务场景、重复机械式操作。不适合：频繁迭代变更、偶尔使用、UI样式细粒度校验、复杂交互临时场景。回归沉淀：迭代中持续沉淀稳定模块用例，区分冒烟用例、全量回归用例，定期清理失效用例、更新适配业务变更。

**3、持续集成：自动化脚本如何接入 Jenkins/GitLab CI？提交代码自动触发冒烟回归？**

1\. 项目打包上传代码仓库，配置Jenkins任务；2\. 配置代码提交触发机制，代码合并/推送后自动构建；3\. 执行自动化冒烟测试套件，运行核心用例；4\. 自动生成测试报告、推送结果通知；实现迭代持续自动化校验，提前拦截线上问题。

**4、场景题：页面列表分页异步加载，如何稳定遍历每一页数据并校验列表正确性？**

**核心方案：**1\. 等待分页组件、列表数据加载完成；2\. 循环获取当前页列表数据，完成字段校验、去重校验；3\. 判断下一页是否可点击，可点击则切换页面，重复执行校验逻辑；4\. 全程添加元素等待与状态判断，避免异步加载导致的漏测、误报，保证全量分页数据校验完整。

**5、版本迭代快，前端频繁改组件、改样式，你的自动化脚本如何保证低维护成本？**

1\. 严格遵循PO模式，页面元素统一封装在页面类，业务用例不直接写定位；2\. 优先使用稳定定位方式，规避动态属性、样式类定位；3\. 通用组件单独封装公共方法，多处复用；4\. 迭代中及时同步页面变更，批量统一更新适配，避免用例大面积失效，大幅降低维护成本。

**6、测试环境不稳定、接口偶尔超时、页面偶尔白屏，如何提升自动化通过率？**

1\. 优化等待策略，适配页面异步加载；2\. 开启用例失败合理重试，仅重试环境类临时报错；3\. 增加页面加载状态、接口请求校验，等待页面完全就绪再执行操作；4\. 规避高峰期执行自动化，清理环境缓存，隔离测试数据，减少环境干扰。

**7、手工 Bug 和自动化 Bug 的区别？自动化适合发现哪类缺陷？**

手工Bug：覆盖用户体验、UI样式、交互细节、场景化复杂BUG；

自动化Bug：聚焦逻辑错误、数据异常、流程阻断、回归引入的兼容性BUG。

自动化擅长：回归BUG、数据计算错误、流程跳转异常、批量操作一致性问题，不适合细粒度UI审美、复杂场景交互测试。

**8、自动化所需数据库、后台账号密码，为什么不能写死在代码里？企业如何安全配置？**

账号、密码、数据库地址、Token等属于敏感信息，直接写死在代码中会随代码提交到仓库，造成**信息泄露、权限安全风险、多环境无法灵活切换**，是自动化框架绝对禁止的写法。企业标准落地方案如下：

1\. **配置文件分离（最常用）**：将账号密码、环境地址、数据库参数统一放入`properties/yml/json` 配置文件，单独放置、不提交公共代码仓库，代码中通过工具类读取配置，实现代码与敏感数据解耦，同时适配测试、预发、线上多环境切换。

2\. **环境变量配置**：本地、Jenkins CI/CD服务器配置系统环境变量，代码动态读取环境变量取值，完全不在项目中留存敏感信息，适合线上流水线执行。
